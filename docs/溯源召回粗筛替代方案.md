# 溯源召回粗筛替代方案（NLCI 弃用后）

> 适用背景：本项目（LicTracer，AI 生成代码许可证合规审计）原用 NLCI 做"溯源召回"的候选召回，
> 但 NLCI 严格依赖 `node >=18 <19`，本环境为 node v22 无法运行，且为外部黑盒、不利可复现/可辩护。
> 现决定弃用 NLCI，重新选型/设计粗筛层。

> ## ✅ 落地状态（2026-08-20 首版 / 2026-08-21 升级为多特征 MinHash 相似召回）
> 本方案**已实现**。采用务实路径 `datasketch`，落地为 `src/provenance/coarse_retriever.py` 的
> **全库确定性 Jaccard 扫描**：MinHash(128, `seed=1`) 签名 + 指纹缓存为底座；对查询 MinHash
> 与全库每个候选做精确 Jaccard 估计并全量排序（O(N×num_perm) 整数级比较，召回确定性 100%）。
> 下游 `redup` 行级精排零改动。
>
> **2026-08-23 更新**：原 `forest`（≥2000 文件用 `MinHashLSHForest` 近似候选生成）分支已移除——
> 本系统 KB 为提取实体集（O(百) 文件），全库扫描在毫秒级完成，Forest 亚线性代价在该规模无收益
> （其 crossover 约在 N≥~20000，见下文第 188–191 行），故仅保留 full 扫描路径。
>
> **2026-08-21 特征管线升级为多特征 MinHash 相似召回**（提升召回率与准确率）：
> - **运算符感知分词**：`re.findall(r"\w+|\S+", ...)` 保留运算符/标点、多字符运算符整体保留，
>   运算符级改动（`x+0` vs `x*0`）在粗筛层即可区分（实测 jaccard 0.5，旧版 1.0 不可区分）；
> - **Winnowing（MOSS 式指纹）**：滑动窗口（默认 15，`LICT_WINNOW_WINDOW`）内取最小 token 哈希，
>   对局部增删改（T3）鲁棒；
> - **AST 子树哈希（Merkle）**：tree-sitter 自底向上计算节点结构哈希（identifier→ID 抗重命名 T2、
>   字面量→类型占位抗常量改写、注释跳过），提供独立于 token 顺序的结构信号；
> - 索引缓存文件名改为 `feature_index.pkl`（含特征管线版本号，旧缓存自动失效）。
>
> 验证结果：原 51.4s/请求（`SequenceMatcher` 全扫描）降至 **6.15ms/请求@100 文件**；精确克隆 top1
> `sim=1.0`、注释级改动视为相同（sim=1.0，T1 正确行为）、**确定性 True**（同输入两次候选集一致）。
> 已知局限（详见 §5）：AST 层字面量类型占位使"仅常量值不同"在 AST 特征不可见，但 token 层保留
> 字面量文本且由下游 `redup` 兜底。

## 0. 问题定位与约束

- **粗筛层在流水线中的位置**：`pipeline.py` 第②步"溯源召回"（`nlci_client.retrieve`），
  从知识库 N 个文件中快速召回 Top-K 候选，交给第③步 `redup` 做行级精排（证据精炼）。
- **当前瓶颈**：`nlci_client._retrieve_fallback` 对**全库每个文件**做
  `SequenceMatcher` 全量比对、零缓存 → 实测 100 文件 × 300 行 ≈ **51.4s/请求**（O(N×M)）。
- **约束**：① 不依赖 node 18；② 最好纯 Python / 轻依赖；③ 确定性、可复现；
  ④ **高精确优先**——许可证合规场景"宁可漏报、不可错判"（独立重写不算侵权）。

## 1. 现有工具调研与对比

### 1.1 方法论前提：合规要"词法精确"，不要"语义相似"

代码克隆分四类（经典分类）：
- **T1 完全一样**（仅空白/注释差异）
- **T2 重命名**（变量/函数名改了，结构一致）
- **T3 近似**（有增删改语句，near-miss）
- **T4 语义等价**（功能相同、结构不同，如冒泡排序 vs 选择排序）

**关键判断**：许可证侵权针对"派生作品"。T4（独立干净重写）在法律上**不构成**派生作品，
不应判为侵权。若用语义嵌入（CodeBERT 等）做粗筛，会把"独立重写"误判为克隆 →
**产生错误侵权结论（高危害误报）**，对合规场景有害。因此粗筛应以词法/Token 方法
（覆盖 T1/T2/T3）为主，语义方法至多作补充信号且不得作为侵权判定门。

### 1.2 候选工具逐评

**A. datasketch —— MinHash + LSH（纯 Python）**
- 机制：k-shingle → MinHash 签名 → LSH 分桶，查询亚线性（O(1) 期望）。
- 准确性：可调（阈值 + `num_perm` + band 数 (b,r)）。Jaccard 阈值 0.5~0.7 覆盖 T1/T2/T3；
  LSH 固有少量 FP/FN，可用"精确重排过滤"消除 FP。
- 时效：索引一次后可缓存；1B 文档级可扩展；查询延迟亚线性（典型 <50ms，vs 当前 51s）。
- 依赖：仅 `datasketch`（pip，纯 Py），**不受 node/Java 版本限制**。
- 结论：**最贴合粗筛需求**；但作为"既有工具"方法贡献度低。

**B. SourcererCC（token 倒排索引，Java，ICSE'16 SOTA）**
- 机制：bag-of-tokens + 优化倒排索引 + token 顺序过滤启发式（本质是"粗筛"的经典实现）。
- 准确性：T1 召回 100%、T2 98%、VST3 93%、ST3 61%；精确率 86%。
- 时效：单机上可扩至 250MLOC；批处理（batch）为主，在线增量查询不友好。
- 依赖：Java（非 node 18，满足约束），但引入 JVM 依赖。
- 结论：**精度/召回的强基线**，适合作为论文对比基准；直接做在线粗筛不如 MinHash 轻。

**C. JPlag（token 成对比较，Java，活跃维护 2026）**
- 机制：源码→Token 序列→字符串匹配，抗重命名/重排；支持 20+ 语言（Python 成熟）。
- 准确性：T1/T2/T3 高；本地计算、不联网。
- 时效：**成对（all-pairs）模型 O(N²)**，随 KB 增长需整库重算，在线增量查询代价高。
- 依赖：Java SE 21/25（非 node 18，满足约束）。
- 结论：适合做**离线批量基线/对比实验**，不适合做在线逐查询的粗筛。

**D. CodeBERT / GraphCodeBERT + FAISS（语义嵌入，torch）**
- 机制：函数级语义向量 + ANN 近邻检索；T4 F1≈96%。
- 时效：亚线性（ANN），延迟 3~30ms（CPU）/ 更低（GPU）。
- 风险：**语义相似 → 对许可证合规是误报源**（把独立重写判为克隆）。
- 结论：**仅作可选补充信号**，且不作为侵权判定门；论文中须明确其局限。

**E. redup（现有，行级结构比对，纯 Py）**——保持不变，作为第③步行级精排。

### 1.3 对比表

| 工具 | 类型 | 依赖 | T1/T2/T3 表现 | 查询时效 | 合规适配度 | 角色建议 |
|---|---|---|---|---|---|---|
| **datasketch (MinHash LSH)** | 词法 shingle | 纯 Py | T1/T2 高、T3 部分 | 亚线性(<50ms) | 高（无误报语义） | ✅ 粗筛实现 |
| **SourcererCC** | token 倒排 | Java | T1 100/T2 98/T3 93(VS) | 批处理 250MLOC | 高 | 基线对比 |
| **JPlag** | token 成对 | Java 21+ | T1/T2/T3 高 | O(N²) 批处理 | 高 | 批量基线 |
| **CodeBERT+FAISS** | 语义嵌入 | torch | T4≈96% F1 | 亚线性 | ⚠️ 语义误报风险 | 可选补充 |
| **redup** | 结构行级 | 纯 Py | 行级精确 | 按候选 | 高 | 精排（不变） |

### 1.4 调研结论

适合做粗筛且不受 node 18 限制的有 datasketch / SourcererCC / JPlag。但 SourcererCC、
JPlag 为批处理/成对模型，在线增量查询不友好且引入 Java 依赖。**对论文最佳路径**：
**自研基于 MinHash/Winnowing 的粗筛**（方法贡献 + 完全可控 + 可复现），并以 SourcererCC、
JPlag 作实验基线对比；务实落地可直接用 datasketch。

## 2. 替代算法设计（自研粗筛层）

### 2.1 总体流程

```
离线（建一次，缓存到磁盘）：
  KB 每文件 → normalize(复用 ast_normalizer) → Token 序列 → k-shingle 集合
           → MinHash 签名(num_perm=128) → 插入 LSH 索引(分 band) → 持久化

在线（每次查询，亚线性）：
  查询代码 → normalize → Token 序列 → k-shingle → MinHash 签名
           → LSH.query(返回阈值以上候选，O(1) 期望)
           → 对少量候选做"精确重排"(Jaccard 或 SequenceMatcher) → 取 Top-K
           → 输出 {file, project, license, similarity} → 交 redup 行级精排
```

### 2.2 关键步骤

1. **规范化（复用现有）**：调用 `ast_normalizer.normalize` 生成规范骨架
   （去注释/空白、变量/函数名统一为 `VAR_n`/`FUNC_n`）→ **天然抗重命名（T2）**，
   比裸文本更鲁棒。
2. **分词**：规范骨架 → Token 序列（关键字/标识符/运算符）。
3. **Shingle**：取 k-gram token 集合（k=3~5，经验值；k 越大越抗局部噪声）。
4. **MinHash 签名**：`num_perm=128`，固定排列（可种子化保证确定性），生成定长签名。
5. **LSH 索引**：将 128 位签名分为 b 个 band、每 band r 行（b×r=128），
   每 band 哈希入桶；索引与 license/project 元数据一并**持久化到磁盘缓存**。
6. **在线查询**：查询签名 → `LSH.query` 得候选（仅返回同桶文件，亚线性）→
   对候选用**精确相似度**（Jaccard 或现有 `SequenceMatcher` ratio）重排 → 取 Top-K。
7. **输出同构**：返回 `[{file, project, license, similarity}]`，
   与现 `nlci_client.retrieve` 输出结构一致 → `redup.refine` 与下游无需改动。

> 可选指纹方案：**Winnowing（MOSS 算法）**——滑动窗口取局部最小哈希作代表指纹，
> 对局部增删改（T3）更鲁棒；可作为 shingle 的替代，二者思路一致。

### 2.3 准确性优化（召回率 / 误报率）

- **召回率**：选 (b,r) 使 Jaccard≈阈值处概率"跳变"（LSH 标准性质）；阈值设 0.5~0.7
  覆盖 T1/T2/T3。MinHash 保证高相似对以高概率被召回，低相似对大概率不召回。
- **误报率（FP）**：LSH 固有 FP；用**精确重排过滤**（仅保留 exact sim ≥ τ 的候选）
  消除 LSH 误报 → 最终精确率高。论文报告：理论 (b,r) 概率曲线 + 重排后实测精确率/召回率。
- **确定性**：MinHash 排列与哈希固定（种子化）→ 给定索引与查询，**候选集确定**
  → 下游合规判定确定，与 PRD"可复现/零幻觉"一致。

### 2.4 时效性优化（吞吐 / 延迟）

- **索引缓存**：建一次、查询零重算——直接消除当前"零缓存"根因（51s 的主因）。
- **亚线性查询**：LSH band 哈希 O(1) 期望，仅对少数候选做精确重排 →
  从 O(N×M) 全扫描降至亚线性。
- **指标目标**：
  - 索引构建：O(N·|tokens|)，一次；
  - 查询延迟：目标 **<50ms**（vs 当前 51s，约 3 个数量级提升）；
  - 吞吐：缓存索引上数千 QPS；
  - KB 扩容：查询耗时近似与 N 无关（仅桶冲突数增长），扩展性远优于全扫描。

### 2.5 输入输出

- **离线输入**：KB 根目录 → 文件清单 + 规范骨架。**离线输出**：LSH 索引文件
  （含每文件 license/project 元数据，持久化缓存）。
- **在线输入**：查询规范骨架（或原始代码，内部规范化）。**在线输出**：Top-K 候选列表
  `[{file, project, license, similarity}]`。

### 2.6 与现有 pipeline 衔接

- 删除 `nlci_client` 的 NLCI 子进程路径与 difflib 全库扫描；替换为 `CoarseRetriever`。
- `redup` 行级精排**完全不变**。
- NLCI 从依赖中移除（Dockerfile / requirements 不再需要 node 18 阶段）。

## 3. 推荐落地方案

- **主干（推荐）**：自研 MinHash/Winnowing 粗筛——方法贡献清晰、纯 Python、可复现、可辩护。
- **务实备选**：直接采用 `datasketch` MinHash LSH——实现快、稳健，适合先跑通端到端。
- **实验基线**：SourcererCC、JPlag（批处理模式）作精度/召回对比。
- **可选增强**：CodeBERT+FAISS 仅作语义补充信号，**不作为侵权判定门**（防误报）。

## 4. 实验评估要点（论文用）

- **数据集**：自构建带 license 标注的 KB + 正负样本对（T1/T2/T3 各比例）。
- **指标**：粗筛召回率/精确率（vs SourcererCC/JPlag 基线）、端到端延迟、KB 扩容扩展性。
- **诚实标注**：语义 T4 不覆盖（合规上不需要，且避免误报）——在"局限性"章节明确说明。

## 5. 已知局限（实现后归档）

1. ~~**粗筛 token 粒度**~~（**2026-08-21 已由 B 解决**）：旧版 `_shingles` 用 `re.findall(r"\w+", skeleton)`
   仅保留标识符与数字、丢弃运算符/标点，致 `return x + 0` 与 `return x * 0` 在粗筛层 jaccard≈1.0 不可区分。
   升级为运算符感知分词（B）后该问题消除（实测 jaccard 0.5）。**现行剩余局限**：AST 层字面量类型占位
   （integer/float→`NUM`、字符串→`STR`）使"仅常量值不同"的改写（`x + 1` vs `x + 2`）在 AST 特征不可见——
   但 token 层（Winnowing）保留字面量文本，该差异在 token 特征可见，且下游 `redup` 行级比对基于真实
   代码文本兜底。
2. **Forest 模式的规模 crossover**：MinHash 128-int jaccard 本就极低廉，原 51s 瓶颈由 `SequenceMatcher` 长序列导致，
   MinHash 全扫描（full 模式）已将其降至毫秒级；`MinHashLSHForest`（forest 模式）的亚线性优势仅在
   N≥~20000 才显著（实测 2000 文件快 4.8×、20000 文件快 77×）。默认切换阈值 `LICT_RETRIEVER_FOREST_MIN=2000`，
   端到端 retrieve 因每次重建查询 MinHash（~8ms 固定开销），小 KB 处 forest 中性偏优。
3. **语义 T4 不覆盖**：方法路线刻意不引入语义嵌入，故功能等价、结构独立的重写不会被粗筛召回——合规上正确（不构成侵权），
   但意味着"有意改写以规避检测"的强克隆无法被粗筛发现，须依赖 KB 覆盖度与 redup 在候选内的比对。
