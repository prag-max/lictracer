## 二、安全问题明细

### P0 — 必须修复

#### S1. redup 硬依赖 → 部署即崩
- **位置**：`src/evidence/redup_adapter.py:14`（顶层 `from redup.core.comparator import compare_projects`）→ `src/pipeline.py:13` 顶层导入链
- **证据**：
  - `requirements.txt` **不含** redup；`requirements-optional.txt` 声明"redup 导入失败时静默跳过"
  - `Dockerfile:7` 只 `pip install -r requirements.txt` → 容器内 `import src.pipeline` 必然 `ModuleNotFoundError`
  - README 方式三"纯标准库离线验证"同样必失败
- **影响**：`docker compose up` 直接崩溃；README 承诺的降级路径从未实现
- **修复**：把 redup 的 import 改为**延迟导入 + try/except**，失败时降级为自研 difflib 行级证据（与 NLCI 降级同模式）；并在 Dockerfile 的 requirements.txt 中补齐或明确移除

#### S2. /analyze 无任何防护 → DoS
- **位置**：`src/api/routes.py:26-33`
- **证据**：`await file.read()` 无大小上限直接读入内存；无认证/API-Key/限流；无 CORS 限制
- **影响**：恶意客户端可并发上传超大/海量文件，触发 tree-sitter 解析 + O(n×m) 比对，耗尽 CPU/内存
- **修复**：
  - 限制上传大小（如 1–5 MB），读取前检查 `Content-Length`，读后用 `len(content)` 二次校验
  - 加简单令牌认证（`Authorization: Bearer` 环境变量）或部署层限流（nginx `limit_req` / API 网关）
  - 非公网场景至少用 uvicorn 的 `--proxy-headers` + 反代配置

#### S3. 500 错误泄露内部异常
- **位置**：`src/api/routes.py:43-44`
- **证据**：`raise HTTPException(status_code=500, detail=f"分析失败：{exc}")`
- **影响**：文件路径、依赖版本、内部实现细节直接回显给客户端，辅助针对性攻击
- **修复**：对外只返回通用 `{"detail": "分析失败，请稍后重试"}`，完整堆栈 `logger.exception()` 记服务端日志

### P1 — 应当修复

#### S4. LLM 调用阻塞请求线程 + 数据外发
- **位置**：`src/reporting/llm_summarizer.py:32-85`；在 `pipeline.py:67` 的同步请求链内
- **影响**：
  - 同步 `urlopen`（30s 超时）发生在请求线程内 → 单请求最长可挂 30s，并发时堆积
  - **上传代码的片段来源/许可证/原因被发送到 OpenAI/DeepSeek**（`user_prompt` 含 `segments`）——若审计对象是客户/专有代码，存在数据外发合规风险（恰与产品主题相悖）
- **修复**：
  - 默认**关闭** LLM 摘要，显式配置才启用；UI 显著提示"启用后代码片段信息将发送至第三方 LLM"
  - 摘要改为异步任务或独立队列；加 `lru_cache` 对相同输入去重

#### S5. Streamlit 公网无鉴权暴露
- **位置**：`docker-compose.yml:12-19`（`--server.address 0.0.0.0`）、`ui/app.py`
- **影响**：公网可直达 8501，无密码；Streamlit 的组件/反序列化历史上有 RCE 类 CVE 面
- **修复**：compose 只映射 `127.0.0.1:8501`；或启用 Streamlit 内置认证（`secrets.toml` + 登录拦截）；建议同 S2 的鉴权方案

#### S6. 依赖安全无保障
- **位置**：`requirements.txt` / `requirements-optional.txt`
- **证据**：`osadl-matrix==2024.5.22.10535`、`tree-sitter==0.26.0`、`redup==0.4.46` 均锁 2024 版；`streamlit>=1.28.0`、`fastapi>=0.104.0` 无上限；无 `pip-audit`/Dependabot 流程
- **修复**：CI 加 `pip-audit`；升级树锁定已知漏洞版本；Dockerfile 用 `pip install` 时允许哈希校验

#### S7. Docker 以 root 运行 + 无健康检查
- **位置**：`Dockerfile:20`（runtime 阶段无 `USER`）；`docker-compose.yml`
- **修复**：`USER nobody`（或专用 uid）；compose 加 `healthcheck`（curl /health）

### P2 — 建议改进

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| S8 | 全库 `except Exception: pass`（config.py / nlci_client.py / matrix_loader.py / license_normalizer.py / ast_normalizer.py） | 静默吞错，真实故障被掩盖（如 YAML 语法错误、矩阵加载失败会静默回退默认值，难以排查） | 至少 `logging.debug`/`warning` 记录；关键路径区分"可降级"与"不应降级" |
| S9 | `routes.py:11` / `cli/main.py:9` / `ui/app.py:11` 顶层 `sys.path.insert` | 运行时修改解释器路径，依赖进程启动顺序，易出隐性 bug | 用 `pyproject.toml`/`setuptools` 安装为包，或入口脚本统一设置 |

## 三、性能问题明细

### P0 — 必须修复

#### P1-1. 相似召回降级路径：全量 O(n×m) 比对 + 每请求重算（实测 51s/请求）
- **位置**：`src/provenance/nlci_client.py:65-82`
- **实测数据**（本机基准）：
  - 100 个 KB 文件 × 300 行，查询 50 行 → **51.4 秒/请求**
  - `difflib.SequenceMatcher(..., autojunk=False)` 5000×5100 字符 ×10 次 → **27 秒**
  - 对照组：`normalize` 9000 行仅 0.039s → **瓶颈 100% 在 difflib 的 O(n×m)，不在解析**
- **根因**：每次请求都重新 `read_file` + `normalize` + 全量 `SequenceMatcher`，知识库骨架**零缓存**；`autojunk=False` 还关闭了 difflib 唯一的大输入优化
- **修复建议**（按投入产出排序）：
  1. **KB 骨架预计算 + 缓存**：`KnowledgeBase` 启动时（或首次）对全部文件 `normalize` 生成骨架并 `lru_cache`，请求间复用（实测可省去每请求 ~50% 时间）
  2. **相似度快速索引**：用 n-gram / 行哈希（如 `set(行骨架)` + Jaccard 粗筛）先过滤掉无关文件，再对 Top 候选跑精确 `SequenceMatcher`；知识库变大时换 `sqlite-vec`/`faiss` 或向量索引
  3. `autojunk` 恢复默认（`True`），或对超过阈值的骨架截断/分块比对
- **提示**：当前知识库仅 2 个文件（实测冒烟 1.18s 全绿），但按 README 定位"高复用基准代码库"扩容后此问题会线性放大

#### P1-2. /analyze 阻塞事件循环
- **位置**：`src/api/routes.py:26`（`async def analyze`）内直接调用同步 `analyze_file`（tree-sitter + difflib + redup + 可能 30s LLM）
- **影响**：FastAPI 在事件循环内执行同步 CPU 密集代码 → **所有并发请求排队**，单请求即拖垮整个服务
- **修复**：改为普通 `def analyze(...)`（FastAPI 自动调度到线程池）；或 `await run_in_executor(None, analyze_file, ...)`；LLM 摘要单独异步化

### P1 — 应当修复

#### P1-3. redup 每次请求全量重跑
- **位置**：`src/evidence/redup_adapter.py:31-55`
- **影响**：每请求创建 2 个临时目录 + `copy2` 全部候选 + `compare_projects` 全量比对；对稍大文件/候选集可到秒级，且与 NLCI 返回结果重复劳动
- **修复**：候选文件缓存（按 `(文件 mtime, size)` 失效）；或仅在 NLCI 命中时启用 redup，降级路径直接走自研 difflib 行级（README 本就宣称如此，当前实现却强制 redup）

#### P1-4. 上传无大小限制
- **位置**：`src/api/routes.py:33`、`ui/app.py:29`
- **影响**：超大文件 → tree-sitter parse 内存暴涨 + difflib 指数级耗时
- **修复**：限制 1–5 MB（同 S2）

### P2 — 建议改进

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| P2-1 | `src/config.py:64-78` | 每次 `analyze_file` 都重新读 YAML + `.env`（`load_settings` 无缓存） | `@lru_cache`；仅显式重载时刷新 |
| P2-2 | `src/reporting/llm_summarizer.py:88-96` | 相同输入重复调用 LLM，烧 token | 结果按 `(status, reason, segments 指纹)` 缓存 |
| P2-3 | `src/pipeline.py:33-43` | `load_settings()` 每请求执行；`top_k` 无上限校验 | 配置加载移出请求路径；`top_k` 钳制到合理区间（如 1–50） |
| P2-4 | `src/preprocessor/ast_normalizer.py:101-129` | 正则兜底路径对长行做多次全量 `re.sub` | 大数据集下可接受，标注即可 |
